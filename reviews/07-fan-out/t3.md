Clause by clause, because a scenario passes only when every line of it does:

- "runs `just keeler-spawn <spec> T2`, T3 and T5, in that order, through
  the same recipe a hand would use" — the stub tmux records one
  `new-session` per spawn, and `started_sessions()` is asserted equal to
  the three session names in the wave's order. That the recipe is the
  same one a hand would run is measured twice: each task has the branch,
  the worktree and the runner `keeler-spawn` cuts, and the recipe body
  itself is asserted to call `keeler-spawn` and never to `git worktree
  add`.
- "every refusal keeler-spawn has still applies per task — a task that
  has become spawned meanwhile is refused and named, and the rest of the
  wave still spawns" — T3's branch is cut behind the run's back, the
  refusal is asserted to be `keeler-spawn`'s own sentence, T3 gets no
  worktree, and T2 and T5 spawn in order regardless.
- "it reports each task's outcome, and exits non-zero if any spawn
  refused" — the two summary lines are read as lines: `spawned` names
  exactly what went out, `refused` exactly what did not, so a run that
  printed neither cannot pass on `keeler-spawn`'s own output further up.
- "the tasks the landing unblocked are the new wave, and the tasks
  already done are listed as done, not offered" — the re-run test lands
  T2 for real (record, tick, merge, `just keeler-land`) and then asserts
  the wave is exactly T4, T1 and T2 read `done`, and T3 and T5 keep the
  board's own word.

Invariants: T3 introduces none of its own. The spec's one stated

### Finding 1 — behaviour no scenario demands: `unset KEELER_FAN_OUT_YES`

`Justfile:902`. Before the loop, `keeler-fan-out` unsets
`KEELER_FAN_OUT_YES` so a spawned agent cannot inherit the human's yes.
The line arrived with T2 as the place T3 would spawn from; T3 kept it and
this branch adds `the_yes_does_not_travel_to_the_agents_it_spawned` to
hold it. It is right — an agent that inherited the answer could run a
wave with the one question that is the human's already answered, which is
the fence the Implementation Notes put up in the very next sentence —
but **no scenario says it**, and the Notes fence only the command files.

Not fixed here, because the fix is a spec amendment and those are the
user's: propose adding to _Yes spawns the whole wave through
keeler-spawn_ a clause such as "And the yes does not travel: the sessions
it spawns are started without KEELER_FAN_OUT_YES set." The test is
already written to it.

`.claude/keeler.md:74-88` carries `<<<<<<< HEAD`, `=======` and

It is **not T3's**: `git show feat/07-fan-out:.claude/keeler.md` has them
too. They came in with `b4ab565 merge(spec-07): T1 — the fork after
approval`, and this task branch inherited them by descending from it.
Left where they are for that reason — resolving another branch's merge
inside T3's diff would put a documentation change nobody asked for into
this pull request, and would conflict a second time with whatever
resolution `feat/07-fan-out` eventually makes.

The resolution is not quite "take one side": the `keeler/07-fan-out/t1`
side is the one that describes the fork and the wave and matches

T14 and so drops the mention of `just keeler-resume <spec> <task>` that

reads oddly under the new numbering, where the wave is step 4;

Worth noting for a later spec: **no gate catches this.** `just dev`,

read `.claude/keeler.md` ask whether the day names the recipes — which
both sides of a conflict satisfy at once. A one-line test that no shipped
file contains a conflict marker would have failed the moment the merge
landed.

### Reviewed and found correct

- The loop suspends `set -e` per task by construction (`if "$just"
  keeler-spawn …; then`), so a refusal is recorded and the wave goes on;
  the closing `if [ -n "$refused" ]` yields 0 when false, so a whole
  wave that spawned exits zero.
- `for id in $wave` is unquoted, but ids come from `keeler-graph`, which
  admits only `T<digits>` — no split or glob hazard.
- `unset` genuinely reaches the grandchild: the nested `just` is a child
  of the recipe's bash, and the stub records what each `new-session` saw
  using `${VAR-<unset>}`, which tells unset from set-empty.
- The `recipe_body` helper really scopes to one recipe, so
  `!body.contains("git worktree add")` is a check and not a vacuous
  truth.
- `.gitignore` gained `/tmux-env`, so the new stub artifact cannot dirty
  the fixture's `git status --porcelain` assertions.
