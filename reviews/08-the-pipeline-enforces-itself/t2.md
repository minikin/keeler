## Findings (settled)

1. **A fail verdict read exactly like no review at all.** The scenario
   asks the gate to fail "naming the record and the contradiction", but
   `Decision::Missing` carried only the task address, so a ticked task
   whose record says `Verdict: fail` produced output identical to one
   nobody had reviewed — sending the reader to write a review that was
   already written. T5 could not have fixed this downstream: the reason is
   known only where the records are weighed, and was thrown away there.
   Fixed test-first in afd40cf: `Why::{Unreviewed, ReviewFailed}` decided
   in `uncovered`, each with its own message, pinned by
   `a_missing_review_and_a_failed_one_do_not_read_alike` and by the
   property model, which now models the reason too.

2. **A test blessed a record the shipped CI job refuses.**
   `the_findings_are_free_form_not_more_headers` carried a second bare
   `Commit:` line in its findings, while `templates/keeler.yml`'s
   `review-record` job — the one T8 adopts into this repository's CI —
   counts `^Commit:` lines and refuses any record but one carrying exactly
   one. Two gates disagreeing about the same file is the failure this spec
   exists to remove. Fixed in afd40cf: the fixture keeps the `Verdict:`
   half, which is real (two records on main open a findings line with it)
   and which CI has no rule against, and says in a comment why `Commit:`
   is left out.

3. **A misfiled record vouched for the wrong task.** The address came
   wholly from the `Spec:` and `Task:` headers, never checked against the
   path. A record copied from its neighbour and not re-headed would vouch
   for the task it was copied from — which reads as reviewed when nobody
   reviewed it — while the task whose file it actually is reads as having
   no record while the file sits right there. The shipped `review-record`
   job does not catch it either: it checks that the path exists and that
   there is one `Commit:` line, never that the headers agree. Fixed
   test-first in 80406b0: the path decides, headers that disagree are
   refused naming both addresses, and `filed_as` says why the path and not
   the headers.

4. **`TaskId::new` lowercases the task id but not the spec slug**, so the
   normalisation T1 argued for was applied to one half of the address.
   Resolved by 3 rather than by lowercasing: a `Spec:` header differing in
   case from the directory it sits in is now a refusal naming both
   spellings, not a silently different address. Lowercasing the slug would
   have been a normalisation the workflow never specifies, and would
   conflate two spec files that differ only in case on a case-sensitive
   filesystem. Pinned by the second half of
   `a_record_filed_under_the_wrong_task_is_refused`.

5. **The `Why::ReviewFailed` message names `reviews/<spec>/<task>.md`**,
   which was only accidentally the failing record's path while finding 3
   stood. With 3 fixed it is true by construction — a record vouches only
   for the task it is filed as — so the message points at the file that
   actually holds the `fail`.

## Left open, for the user

**Proposed spec amendment.** Finding 3's fix adds behavior no scenario
demands: the spec's Implementation Notes say "the gate validates shape and
verdict", and a path/header disagreement is neither. It is kept rather
than flagged-and-dropped because the alternative is a gate whose whole
promise — that no task is ticked without a review — has an exception
documented nowhere, and because it is a case of T2's own scenario "a
malformed record is refused, not misread". If the user prefers the
narrower reading, the change is one function (`filed_as`) and two tests,
and reverting it returns the address to the headers. Suggested wording for
the Acceptance Tests section, should the user want it pinned as a
scenario of its own:

```
Scenario: A record vouches only for the task it is filed as

Given a review record whose `Task:` header names another task
When  the gate runs
Then  it fails, naming the file and both addresses
```
