## Findings (settled)

1. **A Markdown file where records live was refused by accident, not by
   rule.** `read_from` skips a top-level file and a `.DS_Store` but holds
   every `*.md` under `reviews/<slug>/` to the grammar, so a `README.md`
   filed there would fail the gate repository-wide over a file that
   vouches for nothing. The asymmetry was real; the behavior is right and
   was undocumented. Kept and made deliberate in 3b6ebd0: litter the
   operating system leaves is not a claim about a review, a Markdown file
   sitting where records live is, and passing over it would let a record
   misnamed by one letter vanish — its task reading as unreviewed while
   the file sat right there, with nothing naming the file that would have
   explained it. Pinned by
   `a_markdown_file_where_records_live_is_held_to_the_grammar`, which
   checks the refusal names the file and the header it lacks.

2. **The record grammar reaches records by absolute path here.** The
   command hands `parse` the full path it walked to, and T2's
   `the_last_two_components_are_the_address_however_the_path_reaches_them`
   is exactly the test that says that is safe. Checked rather than
   assumed, because a record vouching for the wrong task is the failure
   T2's third finding was about.

## Findings (left open, for the user)

3. **`ci.yml`'s copied `review-record` job pins `actions/checkout@v6`
   while every other job in `ci.yml` and `release.yml` is on `@v7`.** Not
   T5's to fix in either direction: the job is T8's verbatim copy of
   `templates/keeler.yml`, and `this_repository_runs_the_check_it_ships`
   fails the moment the copy and the template disagree. The fix is one
   line in `templates/keeler.yml` followed by a re-copy, in its own change
   — a shipped-workflow edit, which is a decision for the user rather than
   a task branch.

4. **The backlog can carry no heading and no comment**, so
   `reviews/BACKLOG.md` is thirty-nine bare lines and a reader opening it
   is told nothing about what they are. T3 recorded this as T5's problem
   to hit, and it is hit: T3's parser accepts blank lines and task
   addresses, which is exactly what the spec's Implementation Notes
   specify ("one task per line as `<spec-slug>/<task-id>`"). Inventing a
   comment syntax here would be behavior no scenario demands, in the one
   module whose job is refusing lines it was not told about. Two ways out,
   both the user's call:

   ```
   Scenario: The debt list explains itself

   Given a backlog line opening with `#`
   When  the gate runs
   Then  it is a comment, not a task, and the debt list can say what the
         debt is
   ```

   or the explanation lives in CONTRIBUTING beside the `crap-baseline.json`
   paragraph it is modelled on, and the file stays a bare list. T9 already
   opens CONTRIBUTING for the "Nothing enforces this" paragraph, so the
   second costs nothing extra if the user prefers it.
