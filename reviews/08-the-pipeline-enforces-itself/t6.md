## Findings (settled)

1. **The guard checked more than it said, in three places.** Found by the
   built-in review, and it is the same defect the spec exists to remove
   one level down: a check nobody knows they have is one nobody notices
   going away. `ci.yml`'s `version` job runs `release-guard`, so as of
   T6 it is — until T7 lands — the only place the pipeline gate runs in
   CI, under a step named "VERSION, marker and CHANGELOG agree". A
   maintainer would meet it as an unexplained failure about a task.
   Fixed in f31536e: the step names in both workflows say both halves,
   and CONTRIBUTING says it twice — in "What CI checks", and in the
   release checklist with the two ways out (write the record, or put the
   task on `reviews/BACKLOG.md`). Job ids and display names are
   deliberately untouched: those are branch-protection required checks,
   and renaming one is a repository-settings decision.

2. **The success message said the same thing.** `release-guard` printed
   "tag, VERSION, marker, CHANGELOG and N manifest(s) agree" while also
   having run the gate. Now it closes with "and every ticked task is
   accounted for", pinned by an assertion in
   `release_guard_accepts_a_consistent_release`.

3. **A gate that cannot run is a refusal, not a different failure.**
   `skipped_pipeline` turns an unreadable `specs/`, a malformed spec, a
   `reviews/` that is a file and a lying backlog into one more line in
   the same report rather than an early return. Deliberate: the module's
   stated rule is that every disagreement is reported, because stopping
   at the first sends someone round the release loop once per mistake.
   `a_gate_that_cannot_run_at_all_refuses_the_release` pins it, and the
   ordering was checked — `declared_versions(root)?` still short-circuits
   first, so manifest failures keep the message they always had.

4. **The `Gate` enum is why the refactor is an enum and not a struct.**
   `pipeline-check`'s message needs a count of accounted-for ticks, which
   is meaningless beside a refusal; a struct carrying both would hold a
   field no caller may read on one path, and a mutant flipping it would
   survive by construction. The three `(decision, broken.is_empty())`
   arms map one-to-one onto the previous body.

5. **Both release fixtures gained a `specs/`.** `tests/release.rs` is
   spec 02's oracle and its fixtures are unchanged on purpose, so this is
   a deviation worth naming: a repository being released has specs, which
   is the reason spec 04 gave the same fixture a `Cargo.toml`. Nothing in
   either fixture is ticked, so the gate accounts for nothing and spec
   02's scenarios test exactly what they always did — all 374 tests pass,
   and the scenario names and assertions are untouched.
