## Spec conformance

- T7's one scenario, _The gate is one recipe away, everywhere the gates
  live_, has an acceptance test named after it in `tests/pipeline.rs`,
  and it holds both halves the scenario names: `just dev` — the real
  recipe, run over the shipped `Justfile` in a throwaway project with
  cargo stubbed — asks for `cargo xtask pipeline-check`, and
  `.github/workflows/ci.yml` carries a `pipeline-check:` job that runs
  the same command on both of the events the workflow triggers on.
- The Justfile is read by running it, not by reading it. A
  `justfile.contains("cargo xtask pipeline-check")` passes on a command
  sitting in a recipe nothing calls, and says nothing about ordering or
  about whether a refusal reaches the exit code. The stub records what
  cargo was asked for, in order, which answers all three.
- "After the existing gates — it is milliseconds", from the spec's
  Implementation Notes, is pinned as `calls.last()`: the four gates ahead
  of it are minutes, and a pipeline check that ran first would send a
  developer back to the review stage before their tests had compiled.
- "A CI job on push and pull request" is pinned three ways: the
  workflow's `on:` block still names both events, the job exists under
  its own name, and it carries no `if:` — the review-record job's
  `if:` is exactly the shape that would silently take it off one of the
  two events.
- No scope creep. T6's release guard, T9's rules and CONTRIBUTING, and
  the gate's own core are untouched; `Status:` is read by the gate and
  written by nothing here, and T7's box is left for /keeler:mutants.
- T7 is assigned no invariant of its own. Gate soundness, record
  dominance and debt monotonicity are T1's, T2's and T3's, and their
  property tests still run — 372 tests, `just dev` green, CRAP clean at
  59 functions with none above the threshold. The recipe's own line, once
  this task's own box was ticked, is `pipeline-check: 63 ticked task(s)
  accounted for — 24 review record(s), 39 line(s) of accepted debt`.

## Findings settled in this review (fixed at the commit above)

1. **Nothing pinned that a failing gate fails `just dev`.** The cargo
   stub exited zero whatever it was handed, so the recipe body
   `cargo xtask pipeline-check || true` would have satisfied every
   assertion in the test while leaving the gate decorative — the one
   defect that matters most here, since a gate nobody's exit code reads
   is the "comfortable lie" the spec's Context exists to remove. The stub
   now refuses the invocation it is told to refuse, and `just dev` is
   asserted to refuse with it. Verified by falsification: the recipe was
   made to swallow the failure, the test went red naming the swallowed
   call, and the recipe was put back.

2. **`dev`'s dependency line was pinned by prefix, not exactly.**
   `starts_with("dev: fmt lint test crap")` accepts a fifth gate appended
   to the line — `cov`, `mutants-all` — which is precisely the class the
   byte equality it replaced was there to catch. The first line is
   compared exactly again; the two substring bans that remain are about
   the body, which is new ground.

## A spec-06 test that had to move, and why it is not a weakened gate

`tests/branch.rs`'s `the_branch_gate_leaves_dev_alone` asserted
`recipe_block(&justfile, "dev") == "dev: fmt lint test crap"` — the whole
recipe, byte for byte. T7 gives `dev` a body, so that assertion cannot
survive T7 in any form; the question was only whether what it protected
does. It does, in three pieces, and the pieces are stronger than the one
they replace:

- the dependency line is still compared exactly (finding 2 above);
- the branch gate's own `crap-delta` and `mutants-diff` are asserted
  absent from `dev`, which is the thing the test's own comment says it is
  for — the linear road not becoming diff-based behind an adopter's back;
- and the adopter's view, which the old test could only approximate by
  forbidding a body at all, is now *run*:
  `the_gate_stays_out_of_an_adopting_projects_dev` executes the same
  recipe in a project without the marker file and asserts cargo was asked
  for nothing beginning `xtask`, while the four gates it does have ran.

`tests/installer.rs`'s `assert_the_linear_road_is_unchanged` needed no
change: it checks the line, not the block, and the line is unchanged.

## Findings noted and left open

3. **The `just --list` summary for `dev` still reads "format, lint,
   tests, coverage, CRAP".** In this repository it now runs a fifth
   thing. Left as it is deliberately: `just --list` is the adopter's
   road into the Justfile, the body is inert in their project, and
   listing a gate they do not have is the failure mode the spec's own
   non-goal warns about ("their linear road stays documented and
   unenforced, and the rules must say so plainly rather than imply
   otherwise"). The rationale block above the recipe says all of it for
   whoever opens the file.

4. **Where the rules record the new gate is T9's, not T7's.**
   `.claude/keeler.md`'s Quality gates table gains no row here and
   CONTRIBUTING is untouched, because T9 — _The rules stop claiming
   nothing can notice_ — owns exactly that boundary and lists T7 in its
   `Needs:`. Named here so it is not mistaken for an omission.

5. **The two new acceptance tests take ~13 s and ~31 s.** Every
   subprocess they spawn is a trivial shell stub and `just --list` over
   the same file is 4 ms, so the cost is not in the diff; the review's
   generic half could not attribute it either, and the suite's existing
   `just`-driven tests sit in the same range on this machine (24 s for
   `a_graph_mode_recipe_outside_a_git_repository_refuses_in_its_own_voice`,
   16 s for `the_branch_gate_stops_at_the_first_gate_that_fails`). The
   likeliest cause is this machine scanning freshly written executables —
   `just` writes a temp script per shebang recipe, and `dev` reaches four
   of them. Worth a glance if CI's `test` job wall time moves; not worth
   a fix on a guess.
