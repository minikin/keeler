## Part 2 — generic review (`code-review`, high)

Findings, ranked. The two on my own files are fixed in 89c70bf; the rest
name the task that owns the file.

1. **`hooks/session-start.sh` escapes the shellcheck gate.** `just lint`
   (Justfile:60) and `.github/workflows/ci.yml` both run the fixed glob
   `shellcheck install.sh scripts/*.sh`, which never reaches `hooks/` —
   while the comment above it promises "whatever shell lives here gets
   gated, including a script added tomorrow". The new hook is unlinted,
   and `bin/keeler` will be too when T8 lands. **T7 owns `lint`** (spec
   line 995) and T8 owns the wrapper; widening the glob also needs the
   assertion at `tests/xtask.rs:269`, which pins the glob string, to
   follow. Left open deliberately: changing `lint` here would collide
   with T7 in the file the spec assigned to it. The script's two
   branches are exercised by six acceptance tests either way.

2. **The install fixture could reach the network.** `tests/plugin.rs`'s
   `Project::install` stubbed `cargo` but not `curl`, while its doc
   comment claimed the run stays offline; an inherited `KEELER_REF` or
   `KEELER_TARBALL` takes install.sh down its fetch branch
   (install.sh:90). Fixed in 89c70bf with the refusing stub
   `tests/installer.rs` uses, so that case fails loudly instead.

3. **The header credited a gate that does not exist yet.** The script's
   comment said `cargo xtask plugin-check` holds `keeler.md` under 9,500
   bytes; that subcommand is T7's. Fixed in 89c70bf: the comment now
   names `the_rules_fit_the_hook` as today's guard and plugin-check as
   the one that joins it.

4. **The `CLAUDE_PLUGIN_ROOT` guard runs before the adoption check**
   (`hooks/session-start.sh:16`), so an unset variable would make the
   hook exit non-zero in every directory on the machine rather than only
   in Keeler projects. Kept as it is, on purpose: this is the order the
   approved spec writes (line 1046), and Claude Code sets the variable
   for every plugin hook it runs — an unset one is the plugin being run
   wrongly, which is worth one loud complaint rather than silence in the
   directories where the rules were never going to appear anyway. Both
   orders satisfy all six scenarios, so the spec's stands.

5. **`entries()` brace-matches through string literals**
   (`tests/plugin.rs:52`). `hooks.json` is the first manifest with braces
   inside a value, and group extraction works only because
   `${CLAUDE_PLUGIN_ROOT}` is balanced. An unbalanced brace in a future
   command string would break it on valid JSON. Left as it is: the
   helper is T4's, the string it parses is ours and fixed, and a real
   JSON parser here is the second implementation of what `plugin-check`
   will refuse. Worth a line in the backlog if a third manifest arrives.
