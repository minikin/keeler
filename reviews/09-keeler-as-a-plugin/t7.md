The task's three test types are all present: unit tests for the two JSON
field readers and the byte ceiling (`xtask/src/plugin.rs`), the property
`every_disagreeing_source_is_named_exactly_once` — every disagreement
reported, none twice — and the acceptance tests above. Two tests beyond
the scenarios pin what a gate must not do: `a_plugin_that_agrees_passes_
the_check`, without which a check that always refused would satisfy every
scenario here, and `the_release_guard_reports_the_rules_marker_once`.

**Where the marker check lives, and why it is not in two places.** The
release guard already refused a rules marker that disagrees with VERSION,
and `plugin-check` must refuse it too (scenario _plugin-check reads the
rules marker from the plugin root_). Rather than write the comparison
twice, `plugin::marker_disagreement` owns the message and both callers
use it: `guard::disagreements` for the guard, `plugin_check_command` for
the check. `plugin::disagreements` deliberately leaves the marker out, so
the guard — which now runs the plugin check as well — reports it exactly
once. A reader told twice goes looking for a second file to fix, and
there is one.

The message it produces changed with the move: `rules-file marker '…'`
became `keeler.md's marker '…'`, because the scenario asks the check's
output to name `keeler.md`, and because since T4 there is exactly one
place the rules live. Nothing — test, script, workflow or spec — asserted
the old wording.

**Scope.** Four files outside the new module and its tests moved, each
because `release-guard` now reads the plugin's manifests and would
otherwise fail on a fixture that is not a plugin: the fixtures in
`xtask/src/lib.rs`, `xtask/tests/pipeline.rs` and `tests/release.rs` gain
the two manifests, in the style of the `specs/` addition spec 08 made for
the same reason. `tests/common/mod.rs` gains `xtask_bin()` and
`real_just()`, and `tests/thresholds.rs` drops its own copy of the
latter; the harness's shared-fixture module is where both belong. The
guard's success line gains "the plugin" — a guard that checks more than
it says it checks is one nobody knows they are relying on.

**One finding, left open as accepted debt.**

- `tests/common/mod.rs:30` — `xtask_bin()` locates the built binary
  beside the test binary rather than through `env!("CARGO_BIN_EXE_xtask")`,
  which is unavailable to a test target in a package that has no binary
  of its own. There is therefore no cargo dependency edge from this test
  target to the xtask binary: `cargo test --test plugin_check` alone can
  run against a previous build of it, and the existing assertion catches
  only its absence, not its staleness. The gate is unaffected — `just
  test`, and every recipe under `keeler-branch`, run `--workspace
  --all-targets`, which rebuilds it — so this misleads an ad-hoc targeted
  run and nothing else. The pattern predates this task (`tests/release.rs`
  has driven the guard this way since spec 02), and the alternative is an
  unstable cargo feature (artifact dependencies). Recorded rather than
  worked around.

**One observation for a later task, no fix applied here.** CI's `lints`
job inlines `cargo fmt`, `cargo clippy` and `shellcheck` instead of
calling `just lint`, so `plugin-check` reaches CI through the `version`
job's `release-guard` rather than through the recipe. The gate does run
on every push and pull request, but the step is named "VERSION, marker
and CHANGELOG agree, and no review was skipped" — and that file's own
comment argues that a check running under a name that does not mention it
is one nobody knows they have. Renaming the step is a one-line change to
`.github/workflows/ci.yml` that no scenario of this task demands; it is
left for the human to take or leave.
