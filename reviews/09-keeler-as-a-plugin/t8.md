## Part 1 — spec conformance

Seven scenarios, seven tests in `tests/wrapper.rs`, each named after its
scenario:

| Scenario                                                    | Test                                                            |
| ----------------------------------------------------------- | --------------------------------------------------------------- |
| The wrapper runs the plugin's Justfile in the repository root | `the_wrapper_runs_the_plugins_justfile_in_the_repository_root`    |
| The wrapper passes every argument through                     | `the_wrapper_passes_every_argument_through`                       |
| The wrapper passes any argument list through unchanged        | `the_wrapper_passes_any_argument_list_through_unchanged`          |
| The wrapper finds its Justfile through a symlink              | `the_wrapper_finds_its_justfile_through_a_symlink`                |
| Outside a repository the wrapper uses the current directory   | `outside_a_repository_the_wrapper_uses_the_current_directory`     |
| In a linked worktree the wrapper stays in the worktree        | `in_a_linked_worktree_the_wrapper_stays_in_the_worktree`          |
| The wrapper is executable as committed                        | `the_wrapper_is_executable_as_committed`                          |

The one invariant Implementation Notes assigns to this task — "for any
argument list, the recorded list is the fixed prefix plus the arguments
verbatim" — is the property test, and it is a real gate: with `"$@"`
replaced by `$*` it fails and shrinks to `[" "]`, the argument an
unquoted expansion drops. That case is the committed seed in
`tests/wrapper.proptest-regressions`.

Scope: the task line's deliverable is `bin/keeler`, executable in the
index with the hook script and the graph parser, and that is what the
commits add. One deviation from the Implementation Notes' sketch, and
it is deliberate: the sketch execs `just --justfile "$here/../Justfile"`,
which reaches the right file but spells it `<plugin>/bin/../Justfile`.
Two scenarios read that argument back as `<plugin>/Justfile`, so the
wrapper resolves `bin/..` while it is already resolving the symlink —
one `cd -P`, no extra work, and the path a human sees in a message is
the one they would type.

## Part 2 — generic review (`code-review`, high)

Three findings. Ranked, with what happened to each.

1. **The linked-worktree fixture read the log before it checked the
   run** (`tests/wrapper.rs`). A wrapper that failed would have panicked
   with "the stub `just` recorded nothing" rather than its own stderr,
   and the worktree — a sibling of the throwaway repository, not inside
   it — outlived the panic as a stale entry the next run's `worktree
   add` would refuse. Fixed in bf7d776: the worktree lives in a
   directory that removes itself on drop, and the success assertion
   comes first.

2. **`set -u` with `"$@"` and no arguments** was reported as a probable
   abort on bash ≤ 4.3 — which is `/bin/bash` 3.2.57 on macOS, the floor
   the spec states for `readlink -f`. Measured rather than argued: run
   under `/bin/bash` 3.2.57 with zero arguments, the wrapper exits zero
   and hands `just` exactly the four-argument prefix. Bash exempts `$@`
   and `$*` from nounset here, so there is nothing to fix; `${1+"$@"}`
   would be noise. No change.

3. **`git rev-parse --show-toplevel 2>/dev/null || pwd -P` conflates
   every git failure with "outside a repository"** (`bin/keeler:33`).
   Under `detected dubious ownership`, or with git missing, the wrapper
   silently gates the subdirectory the human is standing in instead of
   the project. The finding is real and the line is the approved spec's,
   verbatim (spec line 1063); the only scenario about it is the
   fallback, which the current line satisfies. Telling the two apart is
   new behavior no scenario demands, so it is left as it is and proposed
   as a spec amendment rather than smuggled in here.
