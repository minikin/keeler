The task's stated deliverables all landed: `keeler-top/` as a library
and a thin binary, `Cargo.toml`'s `members`, `keeler-top/tests/top.rs`,
`StreamReader::poll()` with its offset, its trailing-partial buffer and
its shrink-or-second-init reset, and `Record` as a tagged enum.
CLAUDE.md's "the gates measure `xtask/`, and only it" paragraph is
rewritten; the gates now measure two members, and the paragraph says why
they are not alike.

Two of the scenarios needed a fixture that could observe a *negative*,
which is worth naming because a weaker one would have been green for
nothing. "Only the new bytes are read" overwrites the first half of the
already-parsed 1 MB in place, with junk of the same length: the file's
length does not change, so nothing looks like a new run, and a reader
that went back over what it had consumed would find no records there.
"Reads the same at any split" compares the *view* the board keeps —
cleared on a restart — rather than the raw batches, because a split that
puts a second init in the second piece rebuilds the same view by a
different route, and comparing batches would have made the property
false for a reader that is correct.

**Two defects found. One fixed here, one left open because it needs the
user's decision.**

**Fixed: CI lints the root package and nothing else.** `.github/workflows/ci.yml`
ran `cargo clippy --all-targets` with no `--workspace`. The root
manifest is itself a package, so cargo's default members are
`keeler-harness` alone — `xtask/` has been merging unlinted since spec
04, and `keeler-top/` would have joined it on the commit that created
it. This is the exact trap CLAUDE.md's fourth bullet already names
("the shipped recipes already pass `--workspace`; a bare `cargo nextest
run` or `cargo mutants` in this repository silently skips the xtask
member"), sprung in the repository's own CI, and the only symptom was a
gate that failed under `keeler lint` and passed on the pull request.
Fixed in 18e4bdb. Out of T1's stated file list, and taken anyway: no
spec-10 task owns `ci.yml`, and the alternative was to ship a new crate
CI never lints on the very change that adds it. The fix is not pinned by
a test — no suite owns `ci.yml`'s gate steps, and inventing one here
would be a second unrequested change.

**Open, and a proposed spec amendment: the second-init signal does not
cover what the spec says it covers.** The spec's Context section says
the reader "treats a file shorter than its offset, or a second `init`
record, as a new run … the second signal covers a resume that has
already written past the old offset before the board looked." It cannot.
`tee` truncates and rewrites from byte 0, so the new run's init record
lands at the *start* of the file — below the offset, which is where the
old run ended. A poll that happens after the new run has passed the old
offset reads only bytes above it, and the init is never among them. The
shrink comparison does not fire either, because the file is no longer
short. The row then folds the new run's tool calls onto the dead run's
model and context, silently and permanently.

The behavior is implemented as the spec's *Acceptance Tests* section
demands, and that section is the acceptance criteria: the scenario
reads 1 MB replaced by 4 kB, which the length comparison catches, and it
passes. The second-init rule is implemented too, and is exercised by
`a_second_init_record_is_a_new_run_and_the_file_is_read_from_the_start`
— an init arriving above the offset, which is the only way to reach it.
What is wrong is the prose's claim about which resumes are covered, and
the code says so where a reader would look (`stream.rs`, in `poll`).

In practice the hole is narrow: the board polls once a second, `tee`
truncates the moment the resumed runner opens the file, and the new run
takes seconds to write its first record, so the file is essentially
always caught while it is short. It opens only if the board is stalled
across a resume — attached to tmux, or blocked long enough for the new
run to outgrow the old one's length.

**Two ways out, for the user to choose.** Either amend the Context
paragraph to say the length comparison is the rule and the second init
is a belt-and-braces signal for a stream that gains a run above the
offset; or add a scenario for the general case and let the reader track
the file's identity — `st_dev`/`st_ino` plus `mtime`, or the bytes of
the first line — beside the offset. The second is a behavior change and
was not made, because no scenario asks for it.

**One deliberate deviation.** `keeler-top/src/main.rs` prints a refusal
and exits non-zero. No scenario demands it: the command line, `--once`
and the refusals are T5's, and the loop is T6's. It is here because the
task's own text says "lib + bin", and a binary that exists has to do
something; exiting zero having drawn no board is the one thing it must
not do, since that is the failure the rest of this spec exists to
prevent elsewhere. `the_binary_refuses_rather_than_reporting_a_board_it_did_not_draw`
pins it, and T5 replaces both the file and the test.

**Two shapes deferred on purpose, not overlooked.** `Record::Assistant`
and `Record::ToolResult` carry their records' `message` objects
unread — no `parent_tool_use_id`, no `usage`, no timestamp — because
T1's tests cannot observe those and adding fields nothing reads is
implementing ahead of the tests. T2 will need `parent_tool_use_id` at
the record level, which is a top-level field rather than one of
`message`, so it will widen these two variants rather than reach into
the payloads.

**One note for the record: the mutation gate reported timeouts, not
survivors, and the fix was the code.** Three mutants of `consumed +=
newline + 1` — the index advance in the old line-splitting loop — turned
it into an infinite loop, which a test suite can only report as a hang.
The rules say the fix for a survivor is a stronger test; these were not
survivors, and no test could have been stronger, because the mutant
produced no wrong answer to catch. So the arithmetic went: `rposition`
finds the last newline, `split` yields the whole lines before it, and
the tail stays buffered. Same behavior, three timeouts gone, and the
re-run found 27 mutants over the branch with zero survivors.
