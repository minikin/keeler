The task's stated deliverables all landed, in `keeler-top/src/run.rs`:
`Stage` with `Ord` in pipeline order, `ToolCall`, `stage_of(&ToolCall,
worktree)`, the recipe-word rule, worktree-relative path matching,
main-session-only records, and a fold that keeps the maximum.

**The scenario tests go through the parser, not around it.** Every one of
them writes its records to a real stream file and reads them back through
`StreamReader`, because two of T2's rules — the subagent filter and the
shape of a `tool_use` block — are only true of records as the CLI writes
them. A suite that folded hand-built `Record` values would have been
green on a fold that never met the record shape it has to read.

The property asserts two things rather than one. Monotonicity alone is
satisfied by a fold that never moves at all, so it also asserts that the
stage the sequence ends on is the furthest signal in it — the expected
stage travels with each generated line, so the answer is not computed by
the function under test.

**One defect found and fixed: the main-session rule did not reach the init
record.** The null-parent match was written for `assistant` and `user`
records and left `system` ones alone, so a subagent's init record — if the
CLI ever writes one — would have parsed as `Record::Init`. Exactly one
init per run is what makes a second one T1's sign of a resume, so that
record would have rewound the reader and wiped a live view mid-run: the
one record where reading a subagent's is worse than ignoring it. Fixed in
9f67dc1, with the case pinned in `stream.rs`'s unit tests. The comment
beside the match already claimed the rule held for every shape; now it
does.

**Three decisions worth naming.**

**The subagent filter went into the parser, not the fold.** T1's record
predicted this task would "widen these two variants" to carry
`parent_tool_use_id` and let the fold decide. It does not: `Wire` carries
the field and `From<Wire>` turns a parented record into `Record::Other`,
which is precisely what that variant is documented to be — a record the
board does not read. Deciding it once is what makes the spec's "only the
main session counts" true of the stage, the tool, the texts, the usage
and the restart signal at the same time, instead of a rule four later
folds each have to remember. Nothing in the spec wants a subagent's
records; "Subagent activity as its own rows or metrics" is a non-goal.

**`Stage` gained `as_str` and `Display`, which T5 will render with.** The
scenarios are written in the stage's own words — "T1's stage is
`reading`" — and the tests assert those words rather than enum variants,
so the words had to exist to test the scenarios as the spec states them.
They are the stage's vocabulary, not the frame's layout.

**`RunView::ended()` takes no argument, and that is the test.** The
spec's table reads "`.exit` file present, whatever it holds", and the
scenario pairs a `0` with a `1`. A method with nothing to pass cannot
answer differently for the two, so the "whatever it holds" is structural
rather than asserted. What is *not* pinned here is the file lookup
itself: finding `.keeler/runs/<slug>/<tid>.exit` is row assembly, which
is T5's, so this scenario is half-pinned until T5 calls this method from
there. Named so it is not mistaken for finished.

**Open, and a proposed spec amendment: `code-review` may not be the name
the stream writes.** `stage_of_skill` matches the skill name exactly, as
the spec's table states it, and the spec grounds that in three real
streams from spec 09's first wave. But skills reach a session
plugin-qualified in this environment — a `code-review:code-review`
alongside the built-in `code-review` — and if the stream records the
qualified form, the row sits on `qa` for the whole review pass. The
damage is bounded: the same table row gives a second route, the write to
`reviews/<slug>/<tid>.md`, which fires a little later and moves the row
to `review` anyway.

It was left exactly as specified rather than broadened, because
broadening is a behavior change no scenario asks for and the looser match
would also accept some unrelated plugin's `code-review`. **The evidence
could not be gathered here:** this run's own stream is outside the
worktree the session may read, so the one file that would settle it —
`.keeler/runs/10-keeler-top/t2.stream`, which contains this very review's
`Skill` call — was unreadable. If the user wants it settled, the amendment
is one line in the table: accept an optional `<plugin>:` qualifier before
`code-review`, and the check on that stream is `grep -o '"name":"Skill".\{0,80\}'`.
