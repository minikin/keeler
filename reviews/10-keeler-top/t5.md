The task's stated deliverables all landed: `Row` assembly and the state
column (`board.rs`), `layout` and rendering through `TestBackend`
(`frame.rs`), `--once` as plain text, the non-tty refusal and
`keeler-status`'s refusals relayed (`cli.rs`).

**Which fixtures speak, and why they differ.** The two refusal scenarios
run the real plugin: they are about *keeler-status's words*, so the
recipe has to say them, and the board's job is to relay a sentence it did
not write. The frame scenarios use a stub `keeler-status` printing the
report a scenario describes — a frame is a reading of whatever report
arrives, and the states a live wave produces (`running`, `died`, `failed
(exit 1)`) need a tmux session and four spawned agents to produce. That
the stub's format is the recipe's format is not assumed: `status.rs`
carries a round-trip property against the recipe's own `printf`.

**Two things reach past T5's scenarios and are here on purpose.**
`Board::selected` exists because the detail pane is defined as being about
*the selected task*, and `Board::message` because `layout` has to put the
status line somewhere; both are keys T6 and T7 will write to, and neither
has a key that sets it yet.

**`--once` prints the column headings and the rows, and not the ref
line.** The scenario says "a plain table with a header line and one row
per task", and the one beside it says stdout holds only the table. The
ref and the age are the drawn header, checked through `TestBackend`. The
cost is that a script reading `--once` cannot see which ref the board
answered from; if that turns out to matter it is a spec amendment, not a
silent addition.

## The generic review: four findings, three acted on

**A narrow terminal clipped the columns it could not fit.** The tool
column was floored at its minimum instead of the table being allowed to
shrink, so a state as long as `incomplete (no review record, box not
ticked)` composed a 111-column line into a 100-column window and ratatui
cut the right-hand edge off. That is precisely the failure
`Panes::detail`'s own comment says the pane is dropped first to avoid —
and dropping the pane did not avoid it, because the acceptance test used
short states. `widths` became `columns`, which drops columns from the
right, whole, until the tool has its minimum: a column that is gone is
visibly gone, while `f5064` in a clipped COMMIT reads as a commit that
begins `f5064`. Four columns are the floor — task, state, stage, tool —
and they are the four the scenario names.

**`print!` panicked on a closed pipe.** Rust ignores `SIGPIPE`, so
`keeler keeler-top --once <spec> | head -3` returns `EPIPE` from the
write where a shell tool would simply have ended, and the board would
have reported a reader who got exactly what they asked for as a crash.
`written` reads the write's outcome; a broken pipe is not a failure and
every other write error still is.

**Widths were counted in characters and drawn in columns.** `wide`'s doc
said "the terminal's columns" and its body said `chars().count()`. The
command is the one cell that holds whatever the agent typed, and a single
double-width character in it shifted ELAPSED through COMMIT out from
under their headings. `unicode-width` measures both the padding and the
cut now — it was already in the tree, since ratatui builds it for its own
layout, so naming it as a dependency cost nothing but the line.

**The fourth is left as it stands, and it is a real cost.**
`Board::assemble` runs four `git` queries per task per tick, and the
commit list from the fourth is read for the selected row alone: ten tasks
would be forty subprocesses a second once T6 makes this a tick. That is
the spec's own data flow — step 3 of "Every second" lists all four — so
changing it here would be deviating from an approved design in the task
that cannot yet measure the consequence. It belongs to T6, where the
second hand starts.

## The mutation gate: two survivors, both real gaps

`Row::elapsed_column` replaced by the empty string survived. Every row in
every test was drawn against a clock that made the column empty anyway,
so nothing had ever seen it count; a row whose tool has not come back now
reads `02:14`.

`index == selected` flipped to `!=` survived. The selection was drawn and
never asserted, because a `Paragraph` gives a test nothing to read. The
decision moved into `marked`, which returns the lines and their styles —
the headings are never the marked one, and a board with no tasks selects
a row that is not there and marks nothing rather than marking the line
above it.

## One failure that is not explained

**A `just keeler-branch` failed its unmutated baseline once.** Five runs
of the suite at ordinary parallelism, three further `mutants-diff` runs
and two clean `keeler-branch` runs since have not reproduced it, and the
failing baseline log had been overwritten before I thought to read it.
The baseline runs exactly the 165 keeler-top tests, so whatever it was is
in this crate's suite.

What went in is a hypothesis, stated as one: every fixture in this crate
names its directory after the test and the process id, and opens by
removing whatever is at that path. A mutation run is 361 mutants of those
165 tests, four at a time, with a process per test — tens of thousands of
processes in five minutes, which is enough for the pid space to come
round. Two live runs of one test on one name is then not two tests
sharing a directory but one deleting the other's files halfway through,
and the fixtures this task added hold theirs open for seconds while
`just`, `git` and the binary run inside them. `fixture_dir` adds the
instant the process started and a serial that only goes up. The three
unit fixtures share it from `lib.rs`; the two in `tests/top.rs` have
their own copy, since a test target cannot see a `#[cfg(test)]` item in
the library. `git::spec_from_ref` was left alone — it already carries a
serial and makes its directory with `create_dir` rather than adopting
one.

That change reaches into `git.rs` and `stream.rs`, which are T1's and
T4's. Fixing two of the four fixtures and leaving the other two would
have left the gate as flaky as it was for a reason I had already named.

**If it happens again, the thing to do is read
`mutants.out/log/baseline.log` before re-running anything** — a second
run overwrites it, and that is how the first one got away.
