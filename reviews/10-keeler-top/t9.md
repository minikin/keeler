## Findings (settled)

1. **`$ARGS` was glob-expanded, against the plugin's own tree.** The
   argument list has to be unquoted to carry several arguments as
   several, but that leaves pathname expansion on too — and cargo is
   started inside the plugin, which is a repository with a `specs/` of
   its own. `keeler keeler-top 'specs/*.md'` came back with the plugin's
   spec names, not the project's; the test that found it is red without
   the fix and names the file it wrongly resolved to. `set -f` before the
   exec keeps the word splitting and drops the globbing. Fixed in
   f08f199, test first.

2. **`cd "$plugin"` was pinned by nothing.** The stub cargo recorded its
   arguments and not the directory it ran in, so the line that decides
   which `rust-toolchain.toml` rustup honours and whose
   `.cargo/config.toml` applies could be deleted with the suite still
   green. The stub now records `pwd -P` per launch and the first test
   asserts it. Fixed in f08f199.

3. **The first-build probe ignored `CARGO_TARGET_DIR`.** An adopter who
   builds everything into one shared directory has no board under the
   plugin's `target/` at all, so the probe would have promised them "a
   few minutes" on every launch they ever made — the very failure the
   probe's own comment says its path was chosen to avoid. The probe now
   reads `${CARGO_TARGET_DIR:-$plugin/target}`; `[build] target-dir` in a
   config file is not followed, and would need `cargo metadata` on every
   launch to be. Fixed in f08f199. The fixture also clears
   `CARGO_TARGET_DIR` for every launch, so the suite does not answer
   differently on a machine that has one set.

## Findings (left open, for the user)

4. **`graph-mode.md`'s command table does not list `keeler-top`.** After
   this task `keeler keeler-top <spec>` is a real recipe, and that table
   is the plugin's own description of every graph-mode command. It is
   deliberately not added here: T6 and T7 are the loop and the levers,
   and until they land the recipe answers an interactive launch with
   "the live board is not wired up yet — `--once` prints one frame."
   Documenting it now would advertise a board that refuses. The natural
   place is T7 or fan-in, and it is left for the user to place — neither
   `graph-mode.md` nor `README.md` is on spec 10's `Module:` line, and
   T8's review left the same kind of edit flagged for the same reason.

5. **The suite never runs the real binary through the recipe.** Every
   acceptance test here uses a stub cargo, because `cargo run --release`
   compiles ratatui's whole tree and that is minutes inside a test. So
   the manifest path being a manifest, and the binary accepting the flags
   the recipe composes, are checked by hand rather than by the suite. Both
   were checked by hand for this task: the board was launched through the
   recipe against this repository (it drew the nine rows of spec 10, with
   this very task reading `running`), and again against a throwaway
   project root elsewhere, which is what proved the binary is unaffected
   by cargo being started in the plugin. Recorded because it is a hole a
   future change could fall through unnoticed.
