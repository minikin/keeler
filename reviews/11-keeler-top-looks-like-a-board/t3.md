## What was not: the arrow

`board.rs` composes `blocked ← T1` as one string — the state column is one
reading and not two — so the arrow reaches the frame inside the state's own
words rather than through `Theme::waits_on`. theme.rs's own header said as
much and left it there: *a frame that wants the ASCII set has to compose
that text itself*. No frame did, so `KEELER_TOP_ASCII=1` drew `←` in the
one column that most needed the fallback.

`Theme::state_text` swaps it, and three callers go through it: the row, the
detail pane, and the measurement of the state column. The third is the one
that is easy to miss — `<-` is two cells where `←` is one, so a column
sized from the unthemed words cuts the last task a blocked one is waiting
on, which is exactly the reading *a state's reason is never cut* exists to
protect.

`--once` is untouched, and deliberately: it has no theme, and the report a
script parses says `←` from every terminal it is run from.

## What the ASCII scenario does not reach, and why

The scenario names the borders `+-|`. **No panel draws yet** — T4 is where
the frame becomes three bordered boxes — so the border half of that clause
is pinned where it can be, in `theme::tests::the_ascii_theme_replaces_every
_glyph_the_theme_owns`, and will be drawn end to end by T4. The same is
true of `·` and `→`: the theme answers for both, and the header, the pane
and the footer that will use them are T4's and T6's.

The end-to-end sweep asserts that **every line of the table** is ASCII,
heading included. It stops at the last row rather than running to the
bottom of the frame because the detail pane below it is still spec 10's
plain text and carries a `—` between the id and the state. That glyph is
not one the theme owns, and T6's fact block is what replaces it — flagged
here rather than fixed, since fixing it means either changing what the
unicode pane says or giving the theme a mark T1 did not define.
