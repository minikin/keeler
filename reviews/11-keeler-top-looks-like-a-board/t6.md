## What is here that no T6 scenario names

- **`Records`, a supertrait of `Dispatch`.** The Implementation Notes say
  the verdict and the exit go through `Dispatch` so the acceptance tests
  keep stubbing them, and they do — but `Board::assemble` is a function of a
  report, a graph, some streams and two file reads, and handing it the six
  levers as well meant every board a test assembles needed a double that
  could pause a session. The two reads are `Records`; `Dispatch` requires
  it, so a loop that holds one hands it over unchanged.
- **`Row.worktree`.** The notes list four new fields and not this one. The
  paths line names the worktree, the report is where that name is said, and
  the board was throwing it away after the commit column had used it.
- **`Theme::dash` and `Theme::rule`.** The pane draws `—` where there is
  nothing to say and `─` across its section rules, and spec 11's own ASCII
  scenario says no glyph the theme owns may be above U+007F. Both are in
  the theme's table and in the two tests that enumerate it.
- **The verdict is asked only for the rows that could have one.** A record
  is written by a run or landed by a merge, so a task with neither a run nor
  a tick has no branch to hold one and no commit to have brought one. Two
  `git show`s a row a tick is what the read costs, and a board that made
  them every second for every blocked task would spend most of its
  subprocesses on answers that cannot exist.

## Deviations from the Implementation Notes

**`Row.exit` carries the stamp beside the code.** The notes say `exit:
Option<i32>`. The failed task's scenario asks for `ended 04:11 ago`, and
nothing in a run's stream says when it ended — the runner closes the stream
and *then* writes the exit file, so that file's own modification time is the
only clock there is for it. `Exit { code, at }` is one read answering one
question rather than two reads that could disagree.

**The verdict is read from the ref before the task's branch.** The spec's
table says "on the task branch while it exists, on the ref once landed",
which the other order also produces — except where the two disagree, and
there the ref is right. `keeler-status` divides the same way and says why:
a task branch left standing after a merge can hold a verdict from a run
that was later fixed and landed, and reporting it would be reporting
something that no longer happened.

same reason. Both keep their subject:

- **the detail pane shows the selected task's last five texts and its last
  command** — the texts lose their `>` prefix and sit under `── agent ──`,

- **j and k move the selection and the detail pane follows** — the pane no

  every line the board draws.

`frame::detail` and its two unit tests went with it: the pane is
`detail::pane` now, and `frame.rs` hands it the panel's inner size.

## The generic review: six findings, five acted on

Run through the built-in `code-review` skill at high effort over the T6
diff.

1. **The pane could outgrow the panel.** A text block is one of the run's
   turns and can hold a paragraph, so the agent's section was as long as
   what it held — a run that said eight lines pushed `── last command ──`
   past the bottom border, which inverted the rule the code claimed
   (the commits are what a short panel gives up). Every section between the
   fact block and the command is now given what is left, in the order it is
   drawn, and the command itself goes on a panel with room for the fact
   block and nothing else. Two properties pin it:
   `a_pane_fits_the_panel_whatever_the_run_has_said` and
   `a_commit_list_fits_its_room_and_says_what_it_left_out`.
2. **The verdict's read order.** Named above under the deviations: the ref
   answers first now, and the doc comment says why rather than claiming an
   order it did not have.
3. **A commits section with room for nothing but its count.** At one line
   and two commits it drew a rule and `… +2 more` over no commit at all —
   the pane reporting its own arithmetic, which is the thing that section's
   own comment says it avoids. It draws nothing there now:
   `a_commits_section_with_room_for_nothing_but_its_count_says_nothing`.
4. **The cost of the read per tick.** Acted on as above: the rows that could
   have a record are asked about, and no others.
5. **The proptest seed file was untracked.** Committed, with both
   counterexamples the property found while it was being written.
6. **`Unasked`'s documentation had landed on `fixture_dir`'s block**, so one
   was documented as a temporary-directory helper and the other had no docs
   at all. Moved.

The reviewer also noted that `cargo test -p keeler-top` fails two
`terminal::tests` that install process-wide panic hooks. That is not this
diff's: the recipes run the suite under nextest, which gives every test a
process of its own, and under it they pass.

## The gate after it: no CRAP regression, five mutants

**`mutants-diff` found five survivors**, and all five were edges the review's
own fixes had introduced minutes earlier: the `<` where a panel has room for
the command and not a line more; the commits guard's two `||`s; the rows the
verdict is not asked about; and `Shell::verdict`, which had no test that read
a record back through it. Each is a test now — and the guard lost a clause on
the way, since a branch with no commits is over nothing and the empty slice
below it is the same empty answer. A condition no behaviour can tell apart is
one the gate is right to refuse.
